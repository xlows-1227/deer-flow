# DeerFlow 功能优化与新功能路线图

> 生成日期：2026-07-02  
> 参考对标：腾讯 WorkBuddy（职场 AI 工作台：一句话下达 → 多 Agent 并行 → 直接交付文件）  
> 规划项合计：**13**（现有功能优化 6 / 新功能建议 7 / 高优先级 6）

---

## 定位差异（决定取舍）

DeerFlow 是开发者向、可自托管、以 LangGraph + Skill + Sandbox 为核心的通用 super agent；WorkBuddy 是职场人向、桌面本地文件优先的封装型工作台。

DeerFlow **无需照搬桌面形态**，重点补齐以下三块最能提升产品感知的能力：

1. **交付物完整度**
2. **任务可视化**
3. **生态连接器**

---

## 能力对标一览

| 能力维度 | DeerFlow 现状 | WorkBuddy 对标 |
|----------|---------------|----------------|
| 定时任务 | 完善（CRUD/时区/历史） | 后台自动化任务 |
| 数据库连接器 | 基本可用（MySQL/StarRocks） | 多连接器生态 |
| PPT 生成 | 基本可用（专用 Skill） | PPT / 海报技能 |
| Word / Excel 生成 | DOCX 无 · XLSX 仅分析 | 直接写入真实文件 |
| 深度研究 | Skill 方法论 | 15 分钟出结构化报告 |
| 子 Agent 并行 | SubtaskCard 可视化 | 多专家并行 + 过程可视 |
| 任务总览面板 | 雏形（仅列表） | 任务栏（分组/筛选/进度） |
| 模型选择 | 手动 + 模式映射 | Auto 自动调度 |
| 预置专家库 | 无（仅自建 Agent） | 专家中心 + 团队 |
| Skill 市场 | 仅设计文档 | 技能市场 + 社区兼容 |
| 远程下发 | IM channels 已支持 | IM / 小程序远程操控 |

## 现有功能优化（6 项）

### O1 · [高] 统一任务面板 Task Dashboard

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | 现只有 thread 列表 + 侧栏最近定时任务运行（约 8 条），无全局运行中任务、并行进度、状态筛选 |
| 对标 | WorkBuddy 的左侧任务栏是核心入口：按目录分组、多任务并行、随时切换查看进度、按状态筛选 |
| 价值 | Ultra 模式已支持并行 subagent，但用户无法总览「正在跑什么、跑到哪了」。是把 DeerFlow 从「聊天框」升级为「工作台」的关键一步 |
| 落地要点 | 复用已有 per-thread runs API，新增全局 runs 聚合端点；前端做 running/completed/failed 筛选 + 并行进度条 |

### O2 · [中] 结果区新增变更 / Diff 视图

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | 右侧结果区有文件树 + 产物预览，但无对话级变更/diff（diff 仅存在于 Skill 编辑器） |
| 对标 | WorkBuddy 结果区专门有「变更」视图，让用户审阅本轮 Agent 改了哪些文件 |
| 价值 | Craft/执行模式下用户需要可验收的「改了什么」，diff 是建立信任的关键 UI |
| 落地要点 | sandbox 文件按 run 打快照，前端用已有 DiffView 组件渲染本轮新增/修改/删除 |

### O3 · [中] 子智能体实时进度面板

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | SubtaskCard 已在消息流展示状态与最新 tool call，但主要靠 message 解析，非独立实时面板 |
| 对标 | WorkBuddy 强调多 Agent 并行且过程可视，用户能看到 A/B/C 各自在做什么 |
| 价值 | 并行委派是核心差异化能力，可视化能显著提升「多 Agent 在干活」的感知与可控性 |
| 落地要点 | 强化 task_started/running/completed 自定义事件，做成可折叠的并行任务泳道 + 单 subagent 详情 |

### O4 · [高] 深度研究升级为一等公民模式

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | 现以 deep-research 等 Skill 方法论 + web 工具实现，无独立编排、无来源引用面板、无固定报告结构产物 |
| 对标 | WorkBuddy 主打「15 分钟出研究报告」：拆解搜索路径→交叉验证→结构化报告 + 竞品矩阵 |
| 价值 | 深度研究是最高频、最有展示度的办公场景之一，值得从 Skill 提升为带计划/引用/报告模板的模式 |
| 落地要点 | 新增 research 模式：计划步骤可视化、来源引用聚合、自动生成结构化报告（复用文档生成技能） |

### O5 · [中] 模型自动路由（Auto 调度）

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | 只能手动选模型 + 模式映射运行时能力，无按任务类型自动选模型 |
| 对标 | WorkBuddy 提供 Auto 模型调度，并为不同任务标注推荐模型（快速/长流程/视觉/中文写作） |
| 价值 | 降低用户心智负担 + 平衡成本与质量；对多模型部署尤其有价值 |
| 落地要点 | 加轻量 task classifier 或规则路由，配置层声明每类任务的候选模型与降级链，UI 保留手动覆盖 |

### O6 · [高] 前端会话切换稳定性 & 流式取消

| 维度 | 内容 |
|------|------|
| 投入 | S |
| 现状 | 快速切换/新建 thread 时 optimistic 消息不清空、messagesRef 不缩小、进行中的 sendMessage 不取消（见 review 高危项） |
| 对标 | 多任务并行切换是 WorkBuddy 的日常操作，切换必须干净、无串扰 |
| 价值 | 任务面板/并行体验的前提是会话切换绝对可靠，否则并行越多 bug 越明显 |
| 落地要点 | threadId 变化时重置 optimistic/ref、引入 generation token + AbortController 取消在途请求 |

## 新功能建议（7 项）

### N1 · [高] DOCX / XLSX 生成技能（交付物补全）

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | PPTX 有专用生成 Skill；DOCX 无；XLSX 只能读/分析导出 CSV，不能生成 .xlsx 交付 |
| 对标 | WorkBuddy 核心叙事是「直接把结果写进真实的 Word/Excel/PPT 文件，不经过剪贴板」 |
| 价值 | 办公交付物三件套缺两件，是与「办公工作台」定位最直接的差距，投入产出比最高 |
| 落地要点 | 参照 ppt-generation 新增 docx（python-docx）与 xlsx（openpyxl）生成 Skill，输出到 outputs 目录 |

### N2 · [中] 预置专家库 / 专家团队 Expert Center

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | 只有 custom agent（SOUL.md）+ 内置 general-purpose/bash subagent，无预置角色库或团队编排产品形态 |
| 对标 | WorkBuddy 有专家中心：预置专家 + 专家团队，给 Agent 明确角色、方法论、工作流 |
| 价值 | 开箱即用的角色（HR/运营/分析师/研究员）降低上手门槛，是把方法论 Skill 产品化的载体 |
| 落地要点 | 把 consulting-analysis 等方法论 Skill 打包为预置专家，前端 agent 画廊增加「预置专家」分区与一键使用 |

### N3 · [中] Skill 市场 / 分享（落地已有设计）

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | 已有 skill-sharing-permissions 设计草案 v2（待实施评审）；现仅本地 install/upload + 版本历史 |
| 对标 | WorkBuddy 有技能市场，可安装社区技能、兼容 OpenClaw，自然语言创建自定义技能 |
| 价值 | Skill 生态是长期护城河；已有设计文档，落地路径清晰 |
| 落地要点 | 按设计文档实现 skill 分享表 + 权限授予 + 市场浏览/发布；先内网/团队内分享再考虑公开市场 |

### N4 · [高] 扩展 SaaS 连接器（Notion/GitHub/Jira/飞书/Slack）

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | Connectors 平台较完整，但只有 MySQL/StarRocks 数据库类；call_connector_action 已预留扩展位 |
| 对标 | WorkBuddy 强调打通办公生态：Slack/Telegram/Notion/GitHub/Jira/腾讯文档/邮箱/会议/知识库 |
| 价值 | 连接器数量直接决定「能干多少活」。已有连接器框架 + MCP，可快速铺量 |
| 落地要点 | 优先接飞书/Notion/GitHub（读写文档、issue、知识库），部分可直接走 MCP server，沉淀为一等连接器 |

### N5 · [低] 本地文件夹授权批处理

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | DeerFlow 是 Web + sandbox 隔离架构，文件在 thread 隔离目录；无桌面级本地目录授权 |
| 对标 | WorkBuddy 桌面版核心：授权本地文件夹后直接批量整理/重命名/转换本地文件 |
| 价值 | 对「整理本地资料」类场景有独特价值，但与当前 Web/sandbox 架构差异大 |
| 落地要点 | 可选做桌面 agent / 本地目录挂载授权（受控 mount），或以上传+批处理近似替代，优先级偏后 |

### N6 · [低] 团队 / 企业管理（Admin Console）

| 维度 | 内容 |
|------|------|
| 投入 | L |
| 现状 | 有多用户 auth 与 per-user 隔离，但无管理员控制台、团队知识库、统一计费 |
| 对标 | WorkBuddy 企业版：admin 控制台、OneID 统一计费、团队级知识管理 |
| 价值 | 面向企业交付的必备能力，但依赖前面隔离/额度/连接器成熟后再做 |
| 落地要点 | 补管理员角色与控制台、团队共享额度、共享知识库/连接器；建议放在生态成熟后 |

### N7 · [中] 面向用户的用量 / 额度体系

| 维度 | 内容 |
|------|------|
| 投入 | M |
| 现状 | 已有 TokenUsageMiddleware 记录 token，但无面向用户的额度、配额、用量看板 |
| 对标 | WorkBuddy 用 Credits 计量（个人 Pro / 团队共享池），有统一计费 |
| 价值 | 多用户/团队部署时是运营与成本控制的基础，也是商业化前置 |
| 落地要点 | 在 token usage 之上加 per-user/团队额度、用量看板、超额策略；与自定义模型的成本挂钩 |
